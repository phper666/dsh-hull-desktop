# TokenTracker 对账分析：为什么"它准我们不准"是三层假象

> 日期：2026-09-03 · oracle 全景源码分析（TokenTracker 安装版 rollout.js 18239 行 + 本机 db 实测交叉验证）
> 背景：用户多轮反馈数字不准，与 TokenTracker 对照差距 2-161×。本分析用 TT 权威数据（queue.jsonl）正确处理后逐格对账。

## 一、TT queue.jsonl 的真实语义（关键发现）

**queue.jsonl 是追加日志 + 整桶状态重写**：每次 sync（活跃时 20s 一次）把被触碰桶的**当前全量状态**追加写入——同一桶被反复重写成递增的累积快照序列（实测 8/26 某桶 6 条：4.86M→6.45M→…→16.49M）。**消费方必须按 (source,model,hour_start) 去重取最后一条**；直接全量和 = 同一份 token 加 2-5 遍。

## 三、三层假象逐条

1. **对账假象（2-5×）**：queue.jsonl 累积快照全量和（此前所有轮次的"TT 数字"都是这个错误基准）
2. **日界假象（叠加乘数）**：TT UI 按本地时区（UTC+8）分日，queue 桶按 UTC 时间戳落盘；对账脚本按 UTC 日分组 → "zcode 8/31 我们 3.6M vs TT 169M（161×）" = 全量和(3.4×) × 日界(46×) 的完美风暴。**产品代码的 bucketKey 本来就是本地时区**（aggregator.ts new Date(ts).getHours 本地）——假象只存在于对账脚本，不在产品
3. **真实残差（~5%，集中 8/31-9/1，TT 侧虚高）**：TT 快照时点记账永不回缩——sync 时刻看到重试/流式中间快照就累加进桶；diffGeminiTotals 遇 tokens 下降还全量重计（rollout.js:4139-4141）。db 只存最终态，我们读最终态——**8/31+9/1 的 TT 虚高 ~100M，我们更接近真实消耗**

## 四、TT 采集机制要点（对照用）

- opencode：plugin（session.updated → 20s 节流 sync）准实时重扫 db message 表（per-request 快照，与我们同源同口径）+ cursors 水位增量差分 + 30min UTC 桶状态 → queue 重写
- zcode：读 message 表按 providerID 排除 anthropic/openai/google（与我们的 model_usage+GLM 正则等效，两表逐日 token 实测相等）
- dsh：多帧 zstd + lastSeq 水位 + usage disjoint 1:1——与我们实现语义等价（去重后 0.0% 差异实证）

## 五、结论与遗留

1. **适配器不需要再修**（zcode/dsh 精确一致；opencode 多数天 ≤±1%）
2. 产品分桶本就本地时区，无 UTC 分日 bug
3. 8/31-9/1 残差为 TT 侧虚高口径差，不追平（追平唯一路径=装插件请求时点捕获，成本高不建议）
4. 遗留备注：opencode.ts 头注释可补 TT totalReset 全量重计的口径说明（可选）
