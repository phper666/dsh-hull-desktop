# S3 经验沉淀：跨 S 契约登记与代码落地 与 错误码语义单一性

> 三硬标准：可复用 / 非显而易见 / 有代价（均通过）
> 来源：S3 升级编排（dsh-hull-desktop）实现与评审期

---

## Lesson 1：契约登记与代码落地的跨 S 协同——下游开工清单必须显式挂上游待实现项

### 现象
S2 评审修订波（v0.3）登记了契约 **#10 `OverlayManager.swapBack()`**（回滚反向原语）——但那是「契约/设计登记、代码零改动」：S2 侧 swapBack 从未实现。S3 实现时 `Updater.rollback()` 依赖该原语（三步回滚序列的第二步），直到 S3 切片 1 才发现需要先给 OverlayManager 补 swapBack 实现 + 测试。

### 根因
跨 S 变更传播存在「契约登记」与「代码落地」的时间差：登记波只改文档（冻结面声明零改动），落地波在更晚的切片。下游 S 的开工清单若只依赖契约文本，会漏掉「上游代码尚未实现」的事实。

### 对策
- **下游开工清单显式挂上游待实现项**：S3 设计 §7 实现期注记第一条「先给 OverlayManager 补 swapBack() 实现 + 测试，再写 S3 模块」+ 复评 beta 5 条提醒——双保险，才没在实现期踩坑
- 实现期注记要带**顺序约束**（先上游后下游），不只是存在性提醒

### 代价
- 若无双保险：S3 实现到 rollback 时才发现原语不存在 → 中断切片重排（本次双保险已避免）；登记波与落地波之间应保持「登记即排期」的心智模型

## Lesson 2：错误码语义单一性——「系统自动恢复」与「用户主动取消」必须不同码

### 现象
swap 失败但 S2 已内部回滚（overlay phase Ready）时，SwapManager B6 分支抛 `cancelled`——与用户主动取消（Updater B1 分支：swap 返回非 ready）**同码**。S6 设置页按错误码渲染 UI 时，「系统自动回滚成功」会被渲染成「用户取消」，误导。

### 根因
B6 映射时只想着「非 swap-broken」的排除逻辑，没对照已有码的**用户可感知语义**：cancelled = 用户动作，swap-recovered = 系统动作，语义域不同却复用一码。

### 对策
- **内部语义码与契约六码分离**：新增 `swap-recovered`（UPGRADE_ERRORS 内部码，注释非契约六码），与 cancelled 分域；Updater mapSwapError 透传
- 映射表评审时逐码问「这个码在 UI 上怎么渲染」——同渲染 ≠ 同码
- 同类先例：S2 rollback-unavailable 内部码（swapBack 前置失败）也是同一原则的产物

### 代价
- 评审即提出、实现期修复（一轮小修）；若流入 S6 UI 实现期才发现，需回溯 Updater/SwapManager 两层映射 + 改测试，成本更高
