# 数据结构留位 ≠ 功能可用：UI 写图数据必须自带防环守卫（store 校验假设要实测）

| 项 | 内容 |
|:---|:-----|
| 背景 | M2 看板 U-003 依赖图可视化。`dependencies` 数据结构 M2 就留位（store validateDependencies 只查存在/同父/非父），但**无任何 UI 入口**——图做出来默认是空的；且技术方案假设「store 已校验环」实测不成立：编辑表单勾选可直接造 A→B→A 环，store 静默保存，Scheduler 按依赖门控就绪 → **环内任务永久不可调度且无报错**。oracle 评审抓出（中），UI 层补反向边守卫（勾选列表过滤 `s.dependencies.includes(t.id)` 的兄弟）。 |
| 决策或坑 | 两个坑同根：①「数据结构留位」常被误当「功能已可用」——U-003 若严格按 PRD 只做可视化，交付的是看不了数据的图；②对持久层校验能力的假设必须 grep 实测（`validateDependencies` 只查结构合法性不查环），不能凭「契约里写过」推定。写树/图类数据的 UI，环防护要么在 store（权威），要么 UI 侧一行守卫（轻量），**不能两边都不设**。 |
| 影响 | 不这样做：功能交付即死（无可视数据）+ 脏数据静默进存储（环任务永久卡死调度，用户只看到「没跑」无任何错误）。这样做：范围拍板时补最小编辑闭环 + UI 防环守卫；发现模式=「渲染层只读某字段 → grep 该字段有无写入口」。 |
| 适用范围 | 任何「数据结构先行、UI 后补」的功能承接；依赖/引用/图状数据的表单写入；评审时对「store 已校验」类假设的实测。 |
