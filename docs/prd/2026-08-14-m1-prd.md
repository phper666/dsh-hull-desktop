# Hull Desktop（dsh-hull-desktop）M1 PRD

> 版本：v0.1 草稿　|　日期：2026-08-14　|　状态：待评审
> 范围：M1 —— 壳骨架 + dsh 升级编排 + 壳设置页

---

## 1. 背景与定位

**DeepSeek Harness（dsh）** 是 DeepSeek 官方的开源 agent harness（一切皆插件），目前只有 CLI + 浏览器 Web UI 两种形态，没有官方桌面客户端。

**Hull Desktop** 是一个开源 Electron 桌面壳，包住官方 dsh：

- 作为子进程启动/守护/重启 dsh；
- 通过 npm overlay 在壳内完成 dsh 升级（手动触发，原子替换，失败回滚）；
- 渲染官方 Web UI——官方每次升级自动生效，**零 fork、零 patch、零替换**；
- 壳自身的功能全部是增量层（壳原生功能 + 官方扩展点插件），可独立摘除，绝不挡 dsh 的路。

**M1 目标**：让用户能"装一个 dsh-hull-desktop.dmg → 打开 → 自动装好 dsh → 看到官方完整 UI"，并且能在壳里完成 dsh 的升级与回滚。

## 2. 目标用户与场景

| 用户 | 场景 |
|---|---|
| 程序员（主力） | 想要桌面化使用 dsh：不用记 CLI 命令、不用管端口、升级 dsh 不用敲 npm |
| 团队协作成员 | 统一装壳即可用，dsh 版本由壳管理，避免各人环境不一致 |
| 非 Node 用户 | 机器上没装 Node 也能用（壳捆绑 Node 运行时） |

**核心用户故事**：*"我是一个用 dsh 的开发者，我希望打开一个应用就能用 dsh，dsh 出新版时我在设置里点一下就升级，升坏了能一键回退。"*

## 3. 产品原则（不变量，所有迭代必须遵守）

1. **纯壳**：永不 fork/patch/替换 dsh 及其 Web UI；官方每个版本发布当天即可用。
2. **数据官方化**：会话、设置、凭据都在 `DSH_HOME`（默认 `~/.dsh`），壳绝不重新实现或改写。
3. **两条独立升级通道**：dsh 升级（壳内 overlay，手动/可配置自动检查）+ 壳自身升级（后续里程碑引入自更新，M1 不做）。
4. **增量层**：任何需要跑在 dsh 内部的功能只能走官方扩展点。
5. **升级原子性**：staging → 原子替换 → 验证，失败自动回滚；绝不原地修改运行中的副本。

## 4. M1 范围

### 4.1 In Scope

- **壳骨架**：Electron 窗口、启动/守护/重启 dsh 子进程、加载官方 UI、退出/崩溃清理子进程。
- **dsh 运行时管理**：捆绑独立 Node（构建时下载）；首次运行自动安装 dsh 到 overlay；DSH_HOME 默认走官方 `~/.dsh`。
- **升级编排（dsh 通道）**：版本检查（registry）、staging 安装、原子替换、重启验证、自动回滚 + 手动回滚。
- **壳自身升级（Hull 通道，electron-updater，已确认纳入 M1）**：GitHub Releases 分发、手动检查 + 自动检查开关（默认开）、下载后提示重启安装、与 dsh 升级互斥排队。
- **壳设置页**（壳自有的小页面，与官方 UI 分属两个窗口）：**两个升级区块**（dsh 运行时升级 / Hull 应用升级，视觉区隔，各自版本/检查更新/自动检查开关）、dsh 回滚按钮、日志与数据目录入口。
- **托盘**：基础托盘（显示状态、打开主窗口、退出），关闭主窗口默认隐藏到托盘。
- **日志**：dsh 子进程 stdout/stderr 落盘 `<userData>/logs/`，壳事件日志同目录。

### 4.2 Out of Scope（后续里程碑）

- 任务看板（M2+，走官方扩展点插件）。
- 三平台打包（M1 仅 macOS Apple Silicon；代码保持跨平台友好）。
- macOS 公证/签名（需 Apple Developer 账号，M1 不出公证包）。
- 官方 UI 内的壳集成（L1 插件桥）。
- 多实例/多 profile 管理。

## 5. 功能需求

### FR-1 启动与 dsh 就绪

- 壳启动 → 确保 overlay 存在（无则走 FR-2）→ spawn dsh 子进程 → 解析 `dsh web: http://127.0.0.1:<port>` 就绪行 → 主窗口 loadURL。
- 就绪超时（默认 60s）→ 显示失败态 + 日志指引，允许重试。
- 验收：冷启动（已有 overlay）到 UI 可交互 ≤ 10s（不含 dsh 自身启动时间）；dsh 进程崩溃时壳提示并可选重启。

### FR-2 首次安装 dsh

- 无 overlay 时：设置页/启动页显示"正在安装 dsh vX.Y.Z"，用捆绑 npm 执行 `npm install @deepseek-ai/dsh@latest` 到 staging，成功后原子替换为 overlay。
- 安装失败：显示错误 + 重试按钮；网络原因给出 registry 配置入口。
- 验收：全新机器（无 Node、无 dsh）装壳后首次打开即可见官方 UI。

### FR-3 升级检查

- **手动**：设置页「检查更新」按钮 → 查 registry 最新版本 → 有新版弹确认框。
- **自动**：设置页开关（**默认开**，已确认）→ 每次启动静默检查，发现新版弹同样的确认框；开关关闭则完全不检查。
- **确认框信息 = 版本对比 + 变更说明**（已确认）：当前版本 → 新版本两列展示；变更说明尝试从 npm registry（description / release notes）获取，获取不到则降级为纯版本对比。
- registry 地址可在设置页配置（默认官方 npm registry，支持国内镜像）。
- 验收：开关关闭时启动不产生任何网络检查请求；打开时发现新版必弹确认框（含版本对比，变更说明缺失时可降级）。

### FR-4 升级执行

- **会话保护：等当前会话结束再升**（已确认）：确认升级后，先检查会话是否忙碌（agent 是否正在执行任务）：
  - 空闲 → 立即执行升级流程；
  - 忙碌 → 进入**排队等待**状态，提示"升级将在当前会话结束后进行"（托盘/设置页可查看排队状态），会话空闲后自动继续；
  - 等待期间用户可取消排队。
- 执行流程：下载并安装到 `dsh-staging`（进度展示）→ 停子进程 → 原子替换（`dsh` → `dsh-previous`，`dsh-staging` → `dsh`）→ 用新 overlay 重启 → 就绪验证。
- 就绪失败自动回滚（见 FR-5）。
- **依赖**：会话忙碌状态在 dsh 进程内部 → 需要一个 Hull 提供的**宿主插件**（增量层，走官方扩展点 `--patch`，可独立摘除）通过 loopback 暴露"会话忙碌/空闲"状态给壳（见 FR-9）。
- 验收：忙碌时会话不被打断，空闲后自动完成升级；升级全程可中断（用户可取消，取消后保持原版本）；升级成功后 dsh 版本号变化、官方 UI 为新版；原会话/API key 不受影响（DSH_HOME 未动）。

### FR-5 回滚

- **自动**：新版本启动不就绪 → 自动换回 `dsh-previous` 重启，弹窗告知"升级失败已回滚"。
- **手动**：设置页「回滚到上一版本」按钮（有 previous 时可用），停子进程 → 替换 → 重启。
- 验收：注入一个坏版本（模拟）后升级，能自动回到可用版本且数据无损；手动回滚同理。

### FR-6 壳设置页

字段：dsh 当前版本/运行状态/Web 地址；「检查更新」；「自动检查更新」开关（默认开）；registry 输入；「回滚到上一版本」（禁用态按需）；「关闭窗口时退出应用」开关（**默认关**，已确认——默认关闭=隐藏到托盘）；「打开日志目录」「打开数据目录」。
- 验收：设置改动即时生效并持久化（`<userData>/settings.json`）。

### FR-7 退出与清理

- 点关闭：默认隐藏到托盘（设置可改为直接退出）；真正退出（托盘退出/系统退出）时先停 dsh 子进程再退。
- 壳崩溃/被 kill：dsh 子进程不得成为孤儿（子进程随父进程组退出策略 + 启动时兜底清理残留）。
- 验收：退出后 `ps` 无残留 dsh/node 进程；重复启动不产生双实例（单实例锁）。

### FR-8 日志

- `<userData>/logs/hull.log`（壳事件）+ `<userData>/logs/dsh-<pid>.log`（子进程输出，滚动保留最近 3 个）。
- 设置页可一键打开日志目录。
- 验收：升级失败、启动失败等关键路径均有日志可查。

### FR-9 Hull 宿主插件（会话状态桥）

- **动机**：FR-4 需要知道"会话是否忙碌"，该状态在 dsh 进程内部，壳无法直接读取（且直接读 DSH_HOME 违反 CON-R002）。
- **形态**：Hull 随壳分发的一个小宿主插件（npm 包 + `--patch` 挂载，增量层，可摘除），在 dsh 进程内监听会话状态，通过 loopback（本地 socket / HTTP）把"忙碌/空闲"推给壳主进程。
- 插件只做只读的状态暴露，不修改任何 dsh 行为。
- 验收：dsh 挂载该插件后，壳能实时拿到会话忙碌/空闲状态；卸载插件（去掉 `--patch`）后 dsh 功能不受任何影响。

### FR-10 Hull 应用自更新（壳通道）

- **机制**：electron-updater + GitHub Releases（`latest-mac.yml`），与 dsh 升级完全独立（CON-R003）。
- **触发**：设置页「Hull 应用升级」区块——「检查更新」手动按钮 + 「自动检查」开关（默认开，启动时检查，发现新版提示）。
- **确认与安装**：发现新版弹确认框（版本对比 + GitHub Releases 变更说明，缺失降级为版本对比）→ 下载（进度）→ 提示"重启安装"→ 用户确认后：先停 dsh 子进程 → 应用重启安装（electron-updater quitAndInstall）。
- **互斥**：壳升级与 dsh 升级同一时间只允许一个排队（升级队列单槽）；排队中禁用另一个通道的入口。
- **⚠️ 无公证限制**：M1 无 Apple 公证，更新包替换后首次启动可能被 Gatekeeper 拦截——弹窗引导用户右键打开/系统设置放行；正式发布前补公证（PRD 已知限制）。
- 验收：GitHub Releases 发新版本后，壳内检查能发现、下载、重启安装成功；升级期间 dsh 升级入口禁用；升级后壳版本号变化、dsh 数据不受影响。

## 6. 非功能需求

| 项 | 要求 |
|---|---|
| 平台 | 仅打包 macOS Apple Silicon（M1）；**代码跨平台友好**（已确认：process.platform 分支、path.join、进程树清理等从第一天就写好，为 Windows/Linux 铺路但不打包不回归） |
| 性能 | 壳自身空闲内存增量尽量小；启动编排开销 < 1s |
| 安全 | 壳不读取/改写 `DSH_HOME` 内容；renderer 仅经 preload 桥访问壳能力；子进程仅限 127.0.0.1 回环 |
| 网络 | registry 可配置（默认 npm 官方）；断网时所有网络操作优雅降级（提示而非崩溃） |
| 包体积 | 安装包目标 ≤ 150MB（含捆绑 Node + Electron） |
| 稳定性 | 升级任何一步失败都不破坏当前可用版本（原子性 + 回滚兜底） |

## 7. 异常与边界

| 场景 | 行为 |
|---|---|
| 断网启动（已有 overlay） | 正常使用本地 dsh，不检查更新 |
| 断网首次安装 | 失败提示 + 重试 + registry 配置入口 |
| registry 不可达 | 检查失败提示"稍后重试"，不影响运行 |
| 安装中途取消/崩溃 | staging 残留下次启动清理；当前版本不受影响 |
| dsh 启动超时（60s） | 失败态 + 日志 + 重试按钮；升级场景触发自动回滚 |
| 磁盘空间不足 | 安装前预检（估算包大小），失败给出明确提示 |
| 双实例 | 单实例锁，第二个实例唤醒第一个并退出 |
| 升级时用户正在会话中 | 升级前确认（会重启 dsh）；升级完成后会话历史仍可恢复（官方日志持久化） |

## 8. 依赖与风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| dsh 处于 rc 期，CLI 契约（就绪行/参数/入口路径）可能变 | 壳启动/升级逻辑需适配 | 就绪行解析与 spawn 参数收敛为单一模块；随官方发布及时回归 |
| `@deepseek-ai/dsh` npm 包较大（含全部插件） | 首次安装/升级耗时长 | 进度展示 + 国内镜像配置 |
| 无公证的 dmg 首次打开被 Gatekeeper 拦截 | 用户困惑 | README 写明右键打开方式；后续里程碑补公证 |
| 壳自更新在无公证下，更新后启动可能被 Gatekeeper 拦 | 用户升完打不开 | 弹窗引导放行；正式发布前补公证（FR-10 已知限制） |
| 捆绑 Node 版本与官方要求（^22.19 || >=24） | dsh 运行异常 | 构建脚本锁 Node 版本并在 CI 验证 |
