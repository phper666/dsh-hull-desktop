# 恢复类功能的「三态幂等」设计（备份-应用-回滚-补齐）

> 日期：2026-09-17 · 需求：backup（Hull 数据备份与恢复）· 状态：已采用（实现 + 4 轮评审验证）

## 背景

备份/恢复功能的数据生命周期有三个状态共用同一份「预备份」（recovery backup）：**应用包内数据 → 失败回滚 → 无待恢复标记时补齐残留**。三者都会在任意时刻崩溃，要求**任意崩溃点重跑收敛、且任何状态都不丢用户数据**。

## 坑 1：回滚消费预备份 → 续做时删掉已还原的原件

初版：回滚 = ① 删除 userData 中「包内路径」（清掉半应用内容）② 把预备份 `rename` 回原位。
崩溃在 ① 与 ② 之间：部分项已还原（预备份里对应项已被 rename 消费），重启续做时 ① 无条件删除这些「包内路径」→ **刚还原的原件被删，且预备份已无副本 → 不可恢复**。

**修正**：回滚步骤 ② 改 **copy**（预备份不消费）→ 步骤 ① 可以无条件删除（原件永远在预备份里）→ 任意点重跑幂等。

## 坑 2：成功后保留的预备份 + 「缺项即回滚」→ 数周后静默覆盖当前数据

初版：恢复成功后预备份保留（供人工兜底）。但决策表里有一条「无标记 + 预备份有内容 + 某项缺失 → 回滚」。数月后用户删了任一白名单文件（如清空 notes 目录），启动时该分支命中，**把整份当前数据回退到恢复前版本**（静默）。

**修正**（三件套）：
1. **成功后归档**：活跃 `backup/` rename 为 `backup-<ts>/`（保留最新 1 个），活跃态只存在于「恢复进行中」→ 歧义窗口消失；
2. **补齐通道 repair-only**：无标记的补齐**只补缺失、不删不覆盖**（设计原语义本就是"补齐缺失项"）；
3. **异常孤儿绝不自动删**：未完成回滚的旧预备份改名为 `backup-orphan-<ts>/` 保留（改名代替 rm），宁占磁盘不丢数据。

## 坑 3：`manual` 兜底态成为死锁

状态机用 `manual`（需人工介入）保护"现场不可判定"。但「包内独有项在本机两处皆无」（换机恢复常态、apply 中途失败）也命中 → 恢复永久卡死且应用内无出口。修正：copy 式回滚使"两处皆无"安全可续 → `manual` 仅保留「确无源可还原」。

## 可复用清单

- 预备份**只读不消费**（copy 还原），删除集合来自**冻结快照**（staging），而非用户可变的源目录
- 「补齐」与「回滚」是两种语义：补齐只增不改（repair-only），回滚才允许删/覆盖
- 活跃态目录命名显式化（`backup/` vs `backup-<ts>/` vs `backup-orphan-<ts>/`），清理只碰归档不碰孤儿
- 每个状态至少一条「崩溃点重跑」测试（注入 failAt），并显式断言"数据 hash 复原"
